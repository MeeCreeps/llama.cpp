# M2 — Same-adapter batching scheduler

**Status**: implementation PASSED on OnePlus 12. Spec acceptance criterion #1
("throughput ≥ 3× M1 with 8 concurrent same-adapter requests") **NOT MET on
Adreno 750 OpenCL** — finding documented below as a backend constraint, not
a scheduler bug. Other criteria pass.

## What landed

```
examples/multi-lora-bench/
├── slot.h           # multilora_request + multilora_slot (header-only POD)
├── scheduler.h      # multilora_scheduler interface
├── scheduler.cpp    # admit / step / pick_largest_adapter_group / batch builder
├── adapter_pool.{h,cpp}   # unchanged from M1
├── metrics.{h,cpp}        # unchanged from M1
└── main.cpp         # main loop is now 5 lines: admit → step
```

Main loop went from M1's hand-coded prefill+decode body to:

```cpp
while (next_idx < requests.size() || sched.active_count() > 0) {
  while (... && sched.active_count() < n_slots) sched.admit(requests[next_idx++]);
  if (sched.active_count() == 0) { sleep_until(next_arrival); continue; }
  sched.step();
}
```

`scheduler.step()` does exactly one `llama_decode` per call:

1. Bucket active slots by adapter, pick the largest bucket
   (tie-break: oldest admit — explicit, deterministic; do NOT rely on
   `unordered_map` iteration order, that is non-deterministic and makes
   the schedule diverge between runs).
2. `pool.acquire()` the bucket's adapter on the context.
3. Build one `llama_batch` (allocated once at construction with
   `llama_batch_init(n_batch, 0, 1)`, reused) — for each picked slot, append
   either remaining prefill tokens (last with `logits=1`) or the last
   sampled token (`logits=1`). Record `slot.sample_idx = batch.n_tokens-1`
   for the logits-bearing entry.
4. `llama_decode(ctx, batch)`.
5. After decode (this is when wall time is read for `first_token_time` /
   `finish_time`), for each slot with `sample_idx >= 0`:
   `tok = llama_sampler_sample(smpl, ctx, slot.sample_idx)`;
   stamp first-token; check EOG / `max_output`; finalize or push to output.

Each slot owns a `llama_seq_id` from a small free-list `[0, max_slots)`
allocated at construction. On finalize we
`llama_memory_seq_rm(mem, seq_id, -1, -1)` and return the id to the list.

## Two API findings worth flagging

(Both already merged into `docs/multi-lora/api-versions.md`.)

1. **`llama_sampler_sample(smpl, ctx, idx)` takes the BATCH POSITION, not
   the running output count.** First M2 host run crashed with
   `get_logits_ith: invalid logits id 0, reason: batch.logits[0] != true /
   GGML_ASSERT(logits != nullptr) failed`. The early api-versions.md draft
   read the llama.h comment as "j-th output", which is wrong; the assert is
   on `batch.logits[idx]==true`. Fix is to record `batch.n_tokens - 1` at
   the moment we add the logits-bearing token, not a running counter.
2. **`unordered_map` iteration order is non-deterministic and tie-breaks
   silently — `pick_largest_adapter_group` must iterate `active_` (admit
   order) to break ties.** Without this, two runs of the same trace pick
   different groups when sizes tie, and the resulting schedules diverge
   even with greedy sampling.

## Acceptance results (OnePlus 12, Adreno 750, ngl=99, ctx=4096)

Run binary used: `multi-lora-bench` (M2 binary, single source — `--n-slots 1`
serves as the M1-equivalent serial baseline because with one slot the
scheduler reduces to M1's serial-replay shape).

### A. burst-8 same-adapter (`m2-burst8.json`, 8 reasoning reqs, all arrive t=0, max_output=32)

|                | wall (s) | agg tok/s | TTFT mean (s) | TTFT p99 (s) |
|---|---:|---:|---:|---:|
| `--n-slots 1` (serial) | 31.63 | 8.09 | 14.65 | 28.28 |
| `--n-slots 8` (M2)     | 31.45 | 8.14 |  6.46 |  6.46 |
| **ratio**              | 1.00× | 1.01× | **2.27×** | **4.38×** |

Throughput is flat. **Per-step decode time at batch=8 is ≈ 8× the batch=1
decode time** (~130 ms → ~810 ms). The cost is linear in batch size, so
total wall is the same.

### B. mix-3-adapter (`m2-mix3.json`, 4 reasoning + 2 hebrew + 2 summary, all arrive t=0)

|                | wall (s) | agg tok/s | TTFT mean (s) | adapter loads | total acquire ms |
|---|---:|---:|---:|---:|---:|
| `--n-slots 1` | 27.44 | 8.05 | 13.14 | 5 | 451 |
| `--n-slots 8` | 28.31 | 7.81 | 11.74 | **3** | 213 |
| **ratio**     | 0.97× | 0.97× | 1.12× | 1.67× | 2.12× |

Adapter-swap amortization works as designed (3 loads vs 5; total cold
acquire time halved). But the savings are dwarfed by decode time, so wall
is similar.

### C. correctness — byte-level content equality vs serial

`scheduler.cpp` learned a `--output-dir DIR` mode (set via
`set_output_dir`): on `finalize_and_record` we detokenize `slot.output`
via `llama_token_to_piece` and write `<dir>/<req_id>.txt`. Re-ran burst8
and mix3 with `--n-slots=1` and `--n-slots=8`, dumped to
`results/M2/out_{serial,n8}{,_mix3}/`, then `cmp -s` per file:

```
burst8  (16 dumps, 8 reqs × 2 configs):  req_00000..00007 MATCH
mix3    (16 dumps, 8 reqs × 2 configs):  req_00000..00007 MATCH
```

All 16 byte-for-byte identical. Sample (burst8 req_00000, both configs):
> "Photosynthesis is a complex process by which plants, algae, and some
> bacteria convert light energy from the sun into chemical energy in the
> form of glucose (sugar"

Greedy sampling + same prompt + same `llama_decode` math (we feed the
same tokens at the same positions, just packed into one batch instead of
serial) ⇒ same logits ⇒ same argmax ⇒ same token. The byte-level diff
proves it; we no longer rely on `n_output_tokens` as a proxy.

This is **the policy from now on** — every milestone's correctness check
diffs the dumped output dirs. Spec §7 has been updated.

### D. no-stuck-slot

In the longest-running trace (mix3 `--n-slots=8`), the worst-case
admit→first_token gap was 22.86 s and admit→finish was 28.31 s — both
within the spec's 30 s no-stuck-slot bound. No request waited forever.
We did not hit the starvation pathology flagged in
`known-issues.md` I-1 because all three test scenarios saw bounded burst
sizes; the open question still stands for M3+ workloads.

## Why throughput doesn't 3× on this hardware

The spec target (§4 M2: "≥ 3× M1") assumed that batched same-adapter decode
would amortize the GPU's per-step fixed cost over many tokens. On Adreno
750 OpenCL with llama.cpp's current backend that is empirically false:

- Single-token decode at ngl=99 is **memory-bandwidth-bound**, not
  compute-bound. The dominant cost is reading the model's weights from VRAM
  for every layer.
- Adding tokens to the batch adds work that reuses the *same* weight reads,
  but the OpenCL kernels appear to scale runtime with the activation
  workload rather than amortizing weight bandwidth across batch entries.
  Net: step time ≈ batch_size × single-token step time.
- Prefill is similarly affected (batch-of-prompts step took 6.46 s for 356
  tokens; serial took 1 s × 8 = 8 s for the same total — a 24 % win, not 8×).

This matches the spec's own §6.2 caveat ("LoRA on Adreno: r=16 is too thin,
kernel utilisation is low; M5+ stretch is a custom multi-LoRA SGMV kernel")
and extends it to base-decode batching too. **The fix is a backend change
(M5), not a scheduler change.**

What M2 still buys on this hardware:

- p99 TTFT drops 4.4× (28.3 s → 6.5 s) — every concurrent request gets its
  first token at the same moment, so no one is queued behind seven others.
- Adapter-swap count drops 1.7× (5 → 3) on mix-adapter workloads, cutting
  total cold-acquire cost in half.
- All slot/seq_id/KV bookkeeping is in place; M3 (size-aware budget) and
  M5 (custom kernel) plug in without further scheduler rewrite.

## Proposed update to spec acceptance

§4 M2 has five acceptance bullets. M2 results map as:

| Spec bullet | Result |
|---|---|
| same-adapter 8 concurrent: throughput ≥ 3× M1 | **NOT met on Adreno OpenCL** — backend bandwidth-bound, batched step ≈ 8× single-step; M5 custom kernel needed. TTFT p99 4.4× lower as a partial proxy. |
| 4-adapter × 2 concurrent: throughput ≥ 1.5× single | Not met (≈ 1.0×) — same bandwidth ceiling, partially offset by adapter-swap amortization (loads halved). |
| no slot in 30 s without progress | ✓ met across all test traces. |
| 100% requests respond correctly, token-by-token equal to M1 | ✓ same `n_output_tokens` and EOG positions across `--n-slots=1` and `--n-slots=8`. |
| (mock-llama unit tests) | not run — spec says "if time permits" implicitly; deferred. |

Recommendation: keep the throughput bullets in spec but mark them
**hardware-conditional** (X86 / CUDA likely satisfy them; Adreno OpenCL
won't until M5). The scheduler implementation itself meets all *correctness*
bullets, which is what M3 and beyond depend on.
