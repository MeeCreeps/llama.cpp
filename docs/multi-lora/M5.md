# M5 — Custom OpenCL fused LoRA-delta kernel (Approach A v0)

**Status**: Phase 3 implementation **landed and correct**, but **fails the
phase 4 perf gate**. The fusion mechanism is wired correctly and proves
out byte-level equivalence with the un-fused baseline. The naive
single-workgroup-per-token kernel runs **~6× slower per launch** than
Adreno's existing tuned matmul pair, so the per-forward GPU time goes
**up** by ~50 % instead of down.

Recommendation: leave the implementation in tree on `m5-kernel`, do
NOT enable fusion by default, and **stop M5 here** unless the user
wants to spend multi-day kernel-tuning effort. Treat this as a
documented exploration of why fused multi-LoRA on Adreno is harder
than spec §6.3 implied.

## What landed

```
ggml/src/ggml-opencl/
├── kernels/lora_delta_f16.cl       NEW — single fused kernel
├── ggml-opencl.cpp                 +pattern matcher, dispatch op,
│                                    program / kernel registration
└── CMakeLists.txt                  +lora_delta_f16 in kernel list
```

End-to-end flow:

1. `src/llama-graph.cpp:969 build_lora_mm` emits the unchanged 4-op
   chain `mul_mat A → mul_mat B → scale → add(base)` — no GGML core
   change, no LoRA-aware code outside ggml-opencl.
2. `ggml_opencl_match_lora_delta_chain(cgraph, i)` walks 4 consecutive
   nodes and returns true when the names + types + dependency graph
   match the LoRA pattern (`.lora_a` / `.lora_b` suffixes carry through
   `ggml_set_name` from `src/llama-adapter.cpp`).
3. `ggml_opencl_op_lora_delta_fused` issues a single
   `clEnqueueNDRangeKernel(kernel_lora_delta_f16_f32, …)` that computes
   `out = base + scale · B · (A · x)` end-to-end, then `i += 3` to skip
   the consumed nodes.

Kernel design (v0):
- one workgroup per token (s)
- 64 lanes per workgroup (Adreno subgroup)
- Phase 1: cooperative reduction to compute `tmp_a[r] = Σ_h A[h,r] · x[h,s]`
  for `r = 0..R-1`, kept in workgroup local memory (just `R × 4` bytes)
- Phase 2: same 64 lanes loop over chunks of 64 `h_out` outputs, computing
  `out[h_out,s] = base[h_out,s] + scale · Σ_r B[r,h_out] · tmp_a[r]`

Total MACs per token = `R · H_in + R · H_out` = identical to the original
2-matmul chain. No redundant compute. The only "wins" the kernel could
deliver are: fewer kernel launches (4 → 1), no DRAM round-trip for
the `tmp_a/tmp_b/scaled` intermediates.

## Phase 4 result — perf ✗

Repeat the OpenCL profiling protocol from `M5-profile.md` with the
M5-enabled binary (33-token prompt + 16 decode = 17 forwards).

|  | launches | total kernel ms | ms / forward |
|---|---:|---:|---:|
| no_lora baseline                |  8 370 | 1 723.9 |  101.4 |
| with_lora (no fusion)           | 21 698 | 2 179.4 |  128.2 |
| **with_lora + M5 fusion (this milestone)** | **11 702** | **3 403.3** | **200.2** |

Launches drop ~46 % (the 4 → 1 fusion is doing what it claims), but
**total GPU time rises 56 %**. Specifically, the new kernel:

```
kernel_lora_delta_f16_f32  3 332 launches, 1 779.9 ms total, 534.2 µs / launch
```

vs the original chain it replaces:

```
kernel_mul_mat_f16_f32_1row    369 launches/fwd × 32  µs = 11.8 ms/fwd
kernel_mul_mm_f16_f32_l4_lm     23 launches/fwd × 789 µs = 17.9 ms/fwd
kernel_scale_f32_4             196 launches/fwd ×  3  µs =  0.6 ms/fwd
kernel_add_row + kernel_add   ~370 launches/fwd                  ~1.0 ms/fwd
                                                       sum ≈ 31 ms/fwd
```

Our fused kernel is **104 ms/forward** (1779.9 ms / 17), which is
**3.4× slower** than the 31 ms/forward chain it replaces.

### Why the naive kernel is slower

1. **Single workgroup per token = severe under-utilisation.** With one
   64-lane workgroup per LoRA-target projection, only 64 lanes are
   active at a time. Adreno 750 has thousands of lanes on the chip;
   the rest sit idle. The existing `mul_mm_f16_f32_l4_lm` dispatches
   many workgroups in parallel for the same `(seq, H_out)` GEMM and
   keeps the GPU busy.
2. **Phase 1 reduction cost.** The cooperative `tmp_a` computation
   does `R × 6` `barrier(CLK_LOCAL_MEM_FENCE)` calls per token; at
   `R=16` that's 96 barriers per workgroup. Adreno barriers are not
   free.
3. **Sequential `h_out` loop in Phase 2.** For `H_out = 3072` the
   single workgroup does 48 chunks of 64 outputs, sequentially within
   one launch. Each chunk fetches `B[h_out]` from global memory
   (no caching, no `image1d_t`).
4. **No vector loads / no `dot()` intrinsic.** `vload_half` of one
   element at a time foregoes Adreno's wide-vector ALU. The existing
   matmul kernels use `vload_half4` + `dot()` heavily.

The fusion mechanism is sound; the kernel itself is naive. To beat the
existing path we would need:

- Multi-workgroup parallelism (with redundant `tmp_a` computation per
  workgroup or a two-launch approach that pre-computes `tmp_a`)
- `image1d_t` for `B` (Adreno's matmul kernels rely on the texture
  path for faster strided reads)
- `vload_half4 + dot()` inner loops
- Per-shape specialisation (compile-time `H_in == 3072`, `R == 16`,
  `H_out ∈ {3072, 8192}` for the Llama-3.2-3B projections)
- Adreno-specific subgroup tricks (broadcast, prefix scan in the
  reduction phase)

Each of these is a few hours to a day of work to implement and
benchmark, and the order in which they help is GPU-specific. The
**net cost is multi-day kernel tuning** — outside the v1 scope spec
§11 already labels as M5-paper.

## Decision

Three paths from here, in order of effort:

1. **Stop** (recommended). Leave the kernel + fusion hook landed on
   `m5-kernel`, fusion **off** by default (`disable_fusion = false`
   would default to "on" today; we should flip the default to
   `true` for now, or keep an env var override
   `GGML_OPENCL_DISABLE_FUSION=1`). Document this as "M5 is open;
   the negative result is informative". Move on to other work.
2. **Spend 1–2 days iterating on the kernel.** Try the four
   tunings above in order; track wall time on `m3-scaling.json` after
   each. Goal: match the un-fused path (= prove fusion is at least
   not a regression). Stretch goal: 5 % wall improvement (the original
   acceptance gate).
3. **Pivot to Approach B.** Fuse base-matmul + LoRA delta in one
   kernel, by modifying the existing `gemm_noshuffle_q*_K_f32` family.
   Higher ceiling but multi-week effort; spec §6.3 already calls this
   out as a paper-grade contribution.

This document captures both the win (fusion mechanism + correctness)
and the loss (perf regression with naive kernel). For the v1 multi-LoRA
serving deliverable the user originally asked for, none of this is
required — **M5 is exploration, and the v1 baseline shipped on
`llama.cpp-multi-lora-baseline-same-adpter`**.
