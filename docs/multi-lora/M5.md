# M5 — Custom OpenCL fused LoRA-delta kernel

**Status**: PASSED on OnePlus 12 (Adreno 750 OpenCL).

**Headline**: on the M3 41-request Poisson trace `m3-scaling.json`,
m5 fusion drops wall time **200.1 s → 143.5 s, a 28 % reduction**.
Single-token GPU time per forward pass goes **128 ms → 108 ms (–16 %)**,
i.e. the LoRA tax of the un-fused chain (+27 ms / forward) is reduced
by **78 %** to +6 ms / forward.

Phase 3 (correctness) and phase 4 (perf) both pass. Three kernel
iterations were tried; iter 3 lands.

## What landed

```
ggml/src/ggml-opencl/
├── kernels/lora_delta_f16.cl            NEW — two kernels: lora_a + lora_b_scale_add
├── ggml-opencl.cpp                      +pattern matcher, dispatch op (2 launches),
│                                         program / kernel registration
└── CMakeLists.txt                       +lora_delta_f16 in kernel list
```

End-to-end flow when fusion is enabled:

1. `src/llama-graph.cpp:969 build_lora_mm` emits the unchanged 4-op
   chain (`mul_mat A → mul_mat B → scale → add`).
2. `ggml_opencl_match_lora_delta_chain(cgraph, i)` walks 4 consecutive
   nodes; matches when name suffixes `.lora_a` / `.lora_b` (set by
   `src/llama-adapter.cpp`) are present and types are right.
3. `ggml_opencl_op_lora_delta_fused` issues **two** kernel launches:

   ```
   kernel_lora_a_f16_f32           (R, seq) WGs writing tmp_a (size R · seq)
   kernel_lora_b_scale_add_f16_f32 (h_out_groups, seq) WGs writing out
   ```

   Then `i += 3` to skip the consumed nodes (loop's i++ skips the 4th).

The original `mul_mat A` node's GGML-allocated buffer is reused as the
`tmp_a` scratch — no extra allocation. The other two intermediates
(`mul_mat B` output and `scale` output) have allocations but go unused;
the fused kernel writes the final result straight into the `add` node's
output buffer.

### Why two kernels, not one

Across-workgroup synchronization is not available in OpenCL within a
single launch. Single-launch fusion (iter 0/1/2) requires either a tiny
single-workgroup-per-token kernel that under-utilises Adreno (iter 0:
**1.6× slower** than un-fused) or cross-WG redundant `tmp_a` recompute
(iter 1/2). Two launches, with `tmp_a` written to a small scratch
between them, ends up cleanest.

### Per-kernel breakdown (iter 3)

```
kernel_lora_a_f16_f32           3 332 launches, total  50.5 ms, 15.2 µs / launch
kernel_lora_b_scale_add_f16_f32 3 332 launches, total 105.5 ms, 31.7 µs / launch
combined                        6 664 launches, total 156.0 ms,  ≈9.2 ms / forward
```

vs the un-fused chain it replaces (per forward):

```
mul_mat_f16_f32_1row    369 launches × 32  µs ≈ 11.8 ms/fwd
mul_mm_f16_f32_l4_lm     23 launches × 789 µs ≈ 17.9 ms/fwd
scale_f32_4             196 launches ×  3  µs ≈  0.6 ms/fwd
add_row + add          ~370 launches                  ≈  1.0 ms/fwd

```

⇒ the fused kernels do the same work in **9.2 ms/fwd vs 31 ms/fwd** (a
3.4× speedup of the LoRA path itself).

### What each iter taught

**iter 0** (one WG per token, in-WG cooperative reduction):

```c
local_work_size  = (64, 1, 1)
global_work_size = (64, seq, 1)
```

64 lanes leaves Adreno's ~3000 lanes idle. Each WG also paid R · 8 = 128
`barrier(CLK_LOCAL_MEM_FENCE)` calls in phase 1. Result: **6× slower
per launch** than the un-fused matmul pair.

**iter 1** (multi-WG, redundant `tmp_a` per WG, barrier-based reduction):

```
global = (h_out_groups · 64, seq, 1)
```

Better parallelism across WGs (48 WGs / token at H_out = 3072), but
each WG still pays 128 barriers in phase 1. With 48 WGs that's 6 144
barriers per launch — Adreno barrier cost dominated. Slightly slower
than iter 0.

**iter 2** (multi-WG + `sub_group_reduce_add` + `vload4` chunks):

Same WG layout. Replace the in-WG reduction tree with one
`sub_group_reduce_add(...)` per `r`-iteration (no barriers; Adreno
subgroup is exactly the WG size of 64). Read `x` in `float4` chunks;
read `A` row through a `half4 *` cast. Net: per-launch time drops from
~535 µs to 286 µs. **Still 22 ms/fwd slower than un-fused** because of
the 48× redundant `tmp_a` recompute.

**iter 3** (split into two kernels):

```
kernel_lora_a_f16_f32        : compute tmp_a once into mat_a's GGML buffer.
kernel_lora_b_scale_add_f16_f32: compute out from B, tmp_a, base.
```

`tmp_a` is `(R, seq)` ≈ 64 × 512 × 4 B = 128 KB max — small enough that
the existing GGML buffer for the original `mul_mat A` node (which is
otherwise unused) holds it. No extra allocation.

Per-kernel work matches the un-fused version exactly. The wins come from:

1. **Faster `tmp_a` matmul kernel.** Custom kernel A is 15 µs / launch,
   with `vload_half4 + float4` and subgroup reduction. The un-fused
   path's `mul_mat_f16_f32_1row` was 32 µs / launch (and oddly dispatched
   1.88 × per LoRA-projection on average). Saves ~17 µs / projection.
2. **Faster `B @ tmp_a` matmul kernel.** Custom kernel B is 32 µs /
   launch on a 64-lane subgroup reduction. The un-fused path's
   `mul_mm_f16_f32_l4_lm` was 789 µs / launch — that path is GEMM-tuned
   for arbitrary shapes but pays a high fixed cost; for the
   `(seq=1, R=16) → (1, H_out)` shape it is wildly over-provisioned.
3. **Save 2 op-launches per LoRA-projection** (scale and add fold into
   kernel B). Saves ~3 ms / forward of pure launch + minor ops.

That is, the win is mostly **shape-specialisation**: the existing OpenCL
matmul kernels are general-purpose; our two kernels are specialised for
the LoRA-A and LoRA-B shapes (`H_in=3072`, `R=16`, `H_out ∈ {3072, 8192}`)
and pay only what those shapes need.

## Approach B follow-up

`M5-design.md` flagged Approach B (fuse base matmul + LoRA delta) as the
M5-paper unlock. With iter 3 already at +6 ms / fwd LoRA tax, the
remaining 6 ms is dominated by kernel launch overhead and small matmul
fixed costs. Approach B's marginal gain over iter 3 would be at most
~5 ms / forward (3 % wall) — much smaller than its risk and effort
(modifying `gemm_noshuffle_q*_K_f32`). **Recommend NOT pursuing
Approach B**: iter 3 already meets the spec §0.3 success criterion's
"beat vanilla on a metric" threshold (here: wall on a swap-heavy
trace, 28 % faster).

## Toggling fusion

Default: **on**. To disable at runtime (for A/B comparison or
regression isolation):

```bash
GGML_OPENCL_DISABLE_FUSION=1 ./bin/multi-lora-bench-m5 ...
```

This flips `disable_fusion` in the OpenCL backend context; the LoRA
fusion + the existing `NORM`+`MUL`+`ADD` / `RMS_NORM`+`MUL` fusions all
turn off together. Per spec §7.4, this is the baseline configuration
for byte-equality verification on any new fusion work.
