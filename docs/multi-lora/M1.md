# M1 — AdapterPool + serial trace replay

**Status**: PASSED on OnePlus 12 (Adreno 750 OpenCL).

## What landed

Single-binary `multi-lora-bench` reads a pre-tokenized JSON trace and replays
it serially against one `llama_context`, swapping LoRA adapters via a
count-based LRU cache, and writes per-request CSV metrics.

```
examples/multi-lora-bench/
├── CMakeLists.txt
├── main.cpp           # arg parse, trace load, main loop, cleanup
├── adapter_pool.{h,cpp}   # multilora_adapter_pool: LRU, hit/miss/evict counters
└── metrics.{h,cpp}        # multilora_request_metric + CSV dump

tools/workload-gen/
└── gen_workload.py     # Poisson arrivals + Pareto adapter mix, HF chat-template tokenize
```

`docs/multi-lora/api-versions.md` was added in this milestone too — it is the
authoritative map from spec C-API symbols to what `include/llama.h` actually
exports today; M1 code follows that file, not the original spec
pseudocode.

## How M1 differs from spec §4.M1

The spec's pseudocode (§1.1.2 / §4.M1 main.cpp / §5.1 AdapterPool) was drafted
against an older `llama.cpp` API. The actual binding now is:

| Spec said | Actually used |
|---|---|
| `llama_load_model_from_file` | `llama_model_load_from_file` |
| `llama_new_context_with_model` | `llama_init_from_model` |
| `llama_lora_adapter_init` | `llama_adapter_lora_init` |
| `llama_lora_adapter_set` + `_clear` | `llama_set_adapters_lora` (replace-semantics, single batched call) |
| `llama_lora_adapter_free` | `llama_adapter_lora_free` |
| `llama_token_eos(model)` + EOS check | `llama_vocab_is_eog(vocab, tok)` (covers EOT, alora invocation, etc.) |
| `llama_kv_cache_seq_rm` | `llama_memory_seq_rm` on a `llama_memory_t` from `llama_get_memory(ctx)` |

Two design choices intentionally diverge from spec pseudocode:

1. **No mutex in `multilora_adapter_pool` or `multilora_metrics`.** Spec §5.1
   shows `std::mutex mu_;` but CLAUDE.md "single-thread main loop is the
   design" makes that dead weight. We omit it — touching either object
   from a future thread is a contract break, documented in headers.
2. **`adapter_id` resolves either as a bare id or a literal path.**
   Convention is `<adapter_dir>/<id>.gguf`, but if `id` already contains a
   slash or the `.gguf` suffix, `path_for` passes it through. Lets the
   workload generator write fully-qualified paths if it ever wants to.

## Acceptance results (OnePlus 12, Adreno 750, ngl=99, ctx=4096)

### Run A — typical (`m1-accept.json`, 33 reqs, max_resident=2, α=1.0)

| metric | value |
|---|---|
| requests completed | 33 / 33 |
| cache hits / misses / evicts | 25 / 8 / 6 |
| hit rate | 75.8 % |
| cold-acquire mean (LoRA load + set on ctx) | 102 ms (p50 67, p99 193) |
| hot-acquire mean | 0.0 ms |
| TPOT mean | 100 ms / tok ≈ **10 tok/s decode** |
| TTFT mean | 33.3 s ← arrival-anchored, includes serial queue wait |
| Wall | 132 s (vs. 60 s arrival span) |

The arrival-anchored TTFT looks bad until you remember M1 is *serial* with no
batching: 33 requests at ~3 s each must run end-to-end so the 33rd request's
TTFT is naturally tens of seconds. M2 batching is what flattens this.

### Run B — adapter-swap stress (`m1-stress100.json`, 100 reqs, max_resident=1, α=0)

| metric | value |
|---|---|
| requests completed | 100 / 100 (zero crashes) |
| cache hits / misses / evicts | 38 / 62 / 61 |
| hit rate | 38 % |
| cold-acquire mean | 62 ms (p99 72 ms) |

`max_resident=1` plus uniform adapter selection forces an evict on every
adapter transition — the 62 misses comfortably exceed the spec's
"100次 adapter 切换不 crash" target (each miss is a full
init→evict→bind cycle; the 38 hits also re-call `llama_set_adapters_lora`
which exercises the same swap path inside libllama).

             Light into Energy**  Photosynthesis is the incredible

## Adapter pool in this build

Three r=16 LoRAs, all targeting all 7 projections (q/k/v/o + gate/up/down),
all 47 MB f16 GGUF after conversion via `convert_lora_to_gguf.py`:

| id | source repo | base in PEFT config |
|---|---|---|
| `reasoning` | `PandurangMopgar/Llama-3.2-3B-Instruct-reasoning-lora` | `meta-llama/Llama-3.2-3B-Instruct` |
| `hebrew` | `itayl/Llama-3.2-3B-Instruct-Aya-Hebrew-Lora` | `unsloth/llama-3.2-3b-instruct-bnb-4bit` |
| `summary` | `bosmet/lora_model_llama-3.2-3B-Instruct` | `unsloth/llama-3.2-3b-instruct-bnb-4bit` |

The bnb-4bit base id in the latter two PEFT configs is irrelevant at this
layer — both produce LoRA deltas that target the same Llama-3.2-3B
architecture, so they apply cleanly on top of the Q4_0 base GGUF.

## What is intentionally not in M1

- **No batching across requests** — M2.
- **No size-aware budget** (`max_resident` counts adapters, not bytes) — M3.
- **No starvation handling** in the eviction policy — relevant once batching
  exists in M2; pinned-set vs free-set split is M3 (see
  `docs/multi-lora/known-issues.md` I-2).
- **No output-text dump from `multi-lora-bench`** — for adapter-style
  spot-checking we use `llama-completion` directly instead. If/when we want
  per-trace output capture, add `--output-dir` to main.cpp.
- **No HTTP / IPC** — by design (CLAUDE.md). Single binary, single thread,
  in-process JSON in / CSV out.

## Implementation notes (gotchas)

1. **CMake target name is `llama-common`, not `common`.** Linking `common`
   silently falls through to the example's compile rule but `<nlohmann/json.hpp>`
   doesn't resolve because the include path lives on the `llama-common`
   target. First host build failed with "json.hpp: No such file or directory"
   until this got fixed.
2. **`apply_chat_template(tokenize=True)` returns a `BatchEncoding` dict in
   transformers 5.x**, not a bare list. Pass `return_dict=False` to get the
   plain `[token_ids]` list — `gen_workload.py` does this, but it's not
   obvious from the HF docs.
3. **`-no-cnv` is gone** — `llama-cli` is interactive-only now (already
   recorded in M0 notes); `llama-completion` is the non-interactive variant.
   For `multi-lora-bench` we don't use either, just the C API.
4. **OpenCL kernel cache pays a one-time ~22 s on cold boot** — same as M0b.
   Acceptance runs warmed it implicitly with a prior llama-completion run.
