# M6 — Heterogeneous-rank adapter pool

**Status**: PASSED on OnePlus 12 (Adreno 750 OpenCL).

**Headline**: the existing M0–M5 implementation already supports
heterogeneous-rank adapter pools — no scheduler / pool / kernel work
was needed. M6 is the **explicit lifting of the spec §0.2 scope cut
"first version assumes all adapters in pool are r=16"**, validated by
running mixed-rank traces and verifying byte-equality + perf.

## What was actually required

`M5-design.md` already wrote the M5 fused kernel with `R` as a runtime
argument and `LORA_R_MAX = 64` as the local-memory cap. The audit for
M6 (step 1) found:

- **`examples/multi-lora-bench/`**: rank-agnostic. `Slot`, `Scheduler`,
  `AdapterPool` only key on `adapter_id` strings; no rank field
  anywhere. Same-adapter batching automatically respects rank because
  each adapter has fixed rank.
- **`AdapterPool::file_bytes`**: rank-agnostic — uses `stat()` on the
  GGUF file. Larger ranks → larger files → larger `current_bytes_`
  contribution → correct LRU accounting at `--max-adapter-mem-mb` cap.
- **`tools/workload-gen/gen_workload.py`**: rank-agnostic — adapters
  picked by `adapter_id`.
- **`build_lora_mm`** in `src/llama-graph.cpp`: emits matmul nodes whose
  shapes follow each adapter's actual `(H_in, R)` / `(R, H_out)`.
- **M5 fused kernel** (`kernels/lora_delta_f16.cl`): takes `R` as a
  kernel arg, holds `tmp_a` in workgroup-local memory of size
  `LORA_R_MAX = 64` floats. For `R ≤ 64` the fused path runs; for
  `R > 64` `ggml_opencl_match_lora_delta_chain` returns false and the
  graph falls back to the 4 separate ops.

So M6 reduces to: **prove it actually works with a real heterogeneous
pool, and lift the spec scope cut.**

## Byte-equality (per spec §7.4)

### Test 1: `m6-mix4.json` — pool `{r8, r16 (=reasoning), r32, r64}`

8 deterministic-arrival requests, all 4 ranks cycled; `--n-slots 4`,
`--max-adapter-mem-mb 0`, `-ngl 99`. Compare `--output-dir` dumps:

```
GGML_OPENCL_DISABLE_FUSION=1   vs   default (M5 fusion ON):
  req_00000 (r8)        MATCH
  req_00001 (reasoning) MATCH
  req_00002 (r32)       MATCH
  req_00003 (r64)       MATCH
  req_00004 (r8)        MATCH  (cache hit)
  req_00005 (reasoning) MATCH  (cache hit)
  req_00006 (r32)       MATCH  (cache hit)
  req_00007 (r64)       MATCH  (cache hit)
verdict: 8 / 8 MATCH
```

✓ M5 fused kernel behaves byte-identically to the un-fused chain for
every rank in {8, 16, 32, 64}.

### Test 2: `m6-r128-fallback.json` — pool `{r128, reasoning (r=16)}`

4 deterministic-arrival requests cycling between r=16 (fused) and
r=128 (falls through to un-fused 4-op chain because `R > LORA_R_MAX`).

```
GGML_OPENCL_DISABLE_FUSION=1   vs   default:
  req_00000 (r128)      MATCH
  req_00001 (reasoning) MATCH
  req_00002 (r128)      MATCH
  req_00003 (reasoning) MATCH
verdict: 4 / 4 MATCH
```

✓ The fusion-skipped path (r=128) and the fusion-fired path (r=16)
coexist cleanly in the same trace.

## Perf (mixed-rank wall on m6-mix4.json)

| | wall (s) | total tokens | tok/s |
|---|---:|---:|---:|
| `GGML_OPENCL_DISABLE_FUSION=1` | 27.75 | 179 | 6.45 |
| default (M5 iter 3 fusion)     | **21.07** | 179 | **8.49** |

**24 % wall reduction**, throughput +32 %. The M5 fusion benefit holds
across heterogeneous ranks (r=8 / 16 / 32 / 64 all share the same
fused kernel program, just dispatched with different `R` arg).

### Cold-acquire scales with rank (file size)

From the fusion-on `m6-mix4.json` CSV:

| rank | file MB | cold acquire ms | ms / MB |
|---:|---:|---:|---:|
| 8   |  24 |  30.9 | 1.29 |
| 16  |  47 |  89.4 | 1.90 |
| 32  |  93 | 191.0 | 2.05 |
| 64  | 186 | 283.5 | 1.52 |

Roughly 1.5–2.0 ms/MB, consistent with `llama_adapter_lora_init`'s
`fread + memcpy` pattern on Adreno's OpenCL allocator (~600–700 MB/s
effective). All four ranks see the second-use cache hit (acquire = 0
ms), confirming the LRU pool is rank-agnostic.

## What I changed in code

**Nothing in code**. The implementation already supported what M6
needs. The scope of M6 is therefore:

- the spec patch (lift §0.2 scope cut — done in this commit)
- the M6.md write-up (this file)
- result data captured under `results/M6/m6/`

The only behavioural caveat to document is the `LORA_R_MAX = 64`
fusion ceiling — for r > 64 the fused kernel skips and the graph
falls back to the separate matmul + scale + add ops. That fallback is
what an "no fusion" run would do anyway, and it is byte-identical
(test 2 above).

## Caveats / future work

- **`LORA_R_MAX = 64`** can be raised to 128 cheaply (just allocates
  256 bytes more local memory; Adreno 750's ≥ 32 KiB/WG budget has
  ample room). Defer until we see a real workload using r > 64.
- **fp16 accumulator** in the cooperative reduction may underflow
  for very long inner sums (H_in × R ≈ 50K MACs at r=16). For
  Llama-3.2-3B's H_in=3072 it has not surfaced; for larger H_in or
  bigger ranks we may need to split the inner sum or use f32
  accumulation (already what we do in `acc`).
- **Rank-aware scheduler tuning** (spec §11 M6 hint about
  "scheduler 跨组调度") would let the scheduler co-locate
  same-rank requests across adapters to amortise kernel-launch
  overhead even better. We did not need this; keeping
  `pick_largest_adapter_group` keys on `adapter_id` is already
  optimal for our same-adapter batching.
